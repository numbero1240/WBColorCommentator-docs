# 2026-09-29 方針決定

## やったこと
- 作りたいものの整理：Shadowverse: Worlds Beyond の対戦を分析し、最善手と根拠を出す AI
- 入力方法、実行環境、外部 AI の利用有無、利用規約との関係を検討した

## 決めたこと
- **入力は終了済みの対戦の録画だけ。** ライブキャプチャは作らない。
  - 検討した選択肢：画面キャプチャ、メモリ読み取り、通信の傍受。
    メモリと通信は規約違反（第11条第1項第14号など）なので最初に除外した。
  - 画面キャプチャでも、対戦中に最善手を見ながらプレイすると外部ツールの利用（第16号）に当たりうる。
    その使い方は作者自身もしないと決め、さらに「できない」構造にするため入力を録画に限定した。
  - 録画の中にリザルト画面がなければ分析しない。
- **外部の AI API に依存しない。** 盤面の認識は OpenCV ＋ OCR、最善手は自作の探索、
  解説文はテンプレート ＋ ローカル LLM（任意）。GPU は RTX 5070 Ti（16GB）。
- **LLM に判断をさせない。** 計算ミスが出るため、最善手と数値は探索で出し、LLM は文章化だけを担当する。
- **Jev（TypeSafe AI）は現時点では採用しない。** 構造化された状態から選択肢を選ぶ形は相性が良いが、
  クラウド API 専用・画像入力なし・文章を出さない・利用条件が不確実なため。
  評価器を差し替え可能にしておき、将来の比較候補にする。
- **カードデータの扱い**：テンプレート画像は自分の録画から切り出す。効果は独自の形式に書き起こす。
  公式サイトからの一括取得はしない。どちらも外に出さない。
- **公開の範囲**：コードは非公開。方針・設計書・この開発日誌は公開する。
  公開しても「使えないこと」の証明にはならず、動くツールの公開は頒布にあたりうるため。

## 次にやること
- サンプル録画を用意する（リザルト画面まで含むもの）
- M1：録画の読み込み、試合終了の検出、ターンの区切り

# 2026-09-29（続き）サンプル録画の検証

## やったこと
- ゲーム内リプレイを Steam のゲームレコーディングで録画したサンプル 2 本を確認した
  - 1 本目：2560×1440／60fps、約 4 分、1 分あたり約 169MB（WIN で終了）
  - 2 本目：1920×1080／30fps、約 3 分、1 分あたり約 19MB（GAME SET で終了）
- 録画サイズの検証：同じ場面を解像度・ビットレートを変えて再エンコードし、小さい文字の読みやすさを比べた

| 設定 | 1分あたり | 数字 | 手札のカード名 |
|---|---|---|---|
| 1440p／60fps（元の録画） | 169MB | ◎ | ◎ |
| 1080p／30fps／4Mbps | 27MB | ◎ | ◎ |
| 1080p／30fps／2Mbps | 13MB | ◎ | ○ |
| 720p／30fps／2Mbps | 14MB | ◎ | △ |
| 720p／30fps／1Mbps | 7MB | ○ | ✕ |

## わかったこと
- 体力・PP・枚数・攻撃力と体力は、大きいフォントなので 720p でも読める。最初に崩れるのは手札の小さいカード名。
- 終了画面は「WIN」だけでなく「GAME SET」もある。どちらのあとにも「リプレイ終了」のダイアログが出る。
- リプレイ中は画面下にリプレイ専用の操作案内が出る。終わった試合であることの補助的な手がかりになる。
- 進化などの演出が画面全体を覆うことが多い。落ち着いたフレームを選ぶ処理が必要。
- 手札は「開く」と全部読めるが、「選ぶ」効果が発生するたびに閉じる。開いた表示を前提にはできない。

## 決めたこと
- 推奨の録画設定：1080p／30fps／2.5〜4Mbps
- 運用：難しかった試合だけ、あとからリプレイで録画する。分析後は動画を削除できるようにし、盤面の JSON と代表フレームだけを残す
- ファイルの扱いを自動化する：Steam の書き出し先を受け取りフォルダーにし、判定・変換・移動をツールが行う。
  元ファイルの削除は、成功した場合に限り、設定で有効にしたときだけ
- 自分の手札は、マリガンからカードの出入りを追いかけて把握する（開いた表示は任意）
- 他人の対戦：配信アーカイブのダウンロードはプラットフォームの規約上扱わない。
  ゲーム内のルームマッチの観戦を録画する方法を、後の段階で検討する

## 次にやること
- M1：受け取りフォルダーの監視、試合終了の判定、自動変換と移動、試合とターンの区切り

# 2026-09-29（続き）M1：録画の取り込み

## やったこと
- 録画の取り込み処理を実装した：走査 → 試合終了の判定 → 試合とターンの区切り → 代表フレームの保存 → 変換・移動
- 受け取りフォルダー（`data/inbox/`）の監視、コマンド（`wbcc scan / ingest / watch / template`）
- 合成データによるテスト（試合終了の画面がない試合を弾くこと、1 本に 2 試合入っている場合など）

## 判定に使っている手がかり
- **手番**：画面右の手番ボタンの色（青＝自分、赤＝相手）。演出で隠れる短い区間は前後から補う
- **試合の開始**：マリガン画面の「あなたの手番」
- **試合の終了**：「WIN」「GAME SET」の文字
- **代表フレーム**：直前・直後のフレームとの差が小さいもの。「YOUR TURN」「ENEMY TURN」「進化可能」「超進化可能」の
  バナーは動きが少なく落ち着いた画面と誤認するので、テンプレートで検出して除外する

## 結果
- サンプル 3 本とも、試合を 1 件ずつ正しく検出した（18／13／16 ターン）。3 本目では、別の試合から作った
  「WIN」のテンプレートで試合終了を検出できた
- 終了画面のない録画は弾かれ、分析されないことを確認した
- 1440p／60fps の録画は GPU エンコードで 1080p／30fps に変換される（例：55 秒で 155MB → 20MB）
- 処理時間の目安：1080p／30fps の 3 分の録画で約 12 秒

## わかったこと・課題
- 代表フレームに、進化演出の光や相手が出したカードの拡大表示が映ることがある。盤面はおおむね見えているので、
  隠れた部分の検出は盤面認識（M2）で扱う
- 対戦中の画面（リプレイではない録画）では、手札が大きく広がって表示される。リプレイより手札が読みやすい

## 決めたこと
- **自分の対戦のライブ録画も取り込む。** 3 本目のサンプルはリプレイではなく、ランクマッチをそのまま録画したものだった。
  分析できるのは終了画面まで映った録画（試合後に書き出したもの）だけなので、対戦中にツールが画面を見ることはなく、
  POLICY.md の原則 1 と矛盾しない。対戦中の画面は手札が大きく表示されるので認識にも有利で、リプレイを見直す手間もなくなる。
  リプレイ専用の操作案内の有無は記録するが、取り込みの条件にはしない。

## 次にやること
- M2：盤面の数値の読み取り（リーダー体力、PP、手札・山札・墓地の枚数、場のフォロワーの攻撃力と体力）
  - リプレイと対戦中の画面で、手札の位置や操作案内などのレイアウトが違う点に対応する

# 2026-09-29（続き）M2：盤面の数値の読み取り

## やったこと
- 各ターンの代表フレームから、リーダー体力・PP・手札／山札／墓地の枚数・場のフォロワーの攻撃力と体力を読み取り、
  `timeline.json` に保存するようにした。`wbcc show` でターンごとに一覧できる
- OCR は RapidOCR（PaddleOCR のモデルを ONNX Runtime で動かすもの）。1 枚あたり約 0.4 秒

## つまずいたところと対策
| 問題 | 原因 | 対策 |
|---|---|---|
| 「1/6」が「16」、「/7」が「17」になる | 斜線が消える、または「1」に化ける | 文字の位置の検出を使い、斜線を区切りにする。最大 PP は 10 を超えないので、10 を超える「1○」の 1 は斜線とみなす |
| 自分のリーダー体力が読めない | 手札の表示のしかたでリーダーが上下に動く | 固定の位置をやめ、範囲内で大きい赤い盾を探す |
| バッジの数字を読み違える | 数字の部分が色の抽出から抜けて切り抜きが欠ける。枠線を含めると OCR が誤読する | 盾の欠けた部分をまとめてから、数字の部分だけに絞り込む。明るさの反転と元の色の 2 通りで読む |
| ターン開始時の PP が前のターンの値になる | 手番ボタンが変わってから PP が回復するまで 1 秒以上遅れる | PP が回復したフレームを探す。ただし回復した瞬間は引いたカードが盤面を隠すので、盤面・体力は手番が変わった直後のフレームから読んで組み合わせる |
| 「選ぶ」画面の大きなカードを場のフォロワーと誤認する | 同じ色のバッジがある | 緑のコスト表示で見分け、その画面では場を読まない |

## 結果
- サンプル 3 試合（47 ターン）のターン開始時の状態で、読めなかった値は 4 か所
  （カードに隠れたリーダー体力、相手のターン中の自分の最大 PP が 2 か所、演出と重なった体力バッジ）
- 全項目を目視で照らし合わせたのは 2 フレーム（リプレイと対戦中の画面を 1 枚ずつ）で、誤りはなかった。
  それ以外のターンは、最大 PP が毎ターン 1 ずつ増える、手番側の手札がターン開始時に 1 枚増える、
  といった流れに矛盾がないことを確認した（全数の目視確認はしていない）

# 2026-09-29（続き）M3：カードの特定（場のフォロワー）

## 方針
- 自分の録画から切り出したカード画像を見本にする。公式サイトのカード画像は使わない
- 「自動でグループにまとめる → 人がグループにカード名を付ける → 以降は自動で判別する」という流れ
- 名前付けは YAML ファイルに書き込む方式（一覧画像を見ながら `g001: カード名` と書く）。
  専用の Web 画面は M5 で Web UI を作るときに検討する

## 比べ方の検討
- 最初は縮小した画像どうしの相関で比べたが、同じカードが 2〜5 グループに分かれた（203 枚 → 45 グループ）
- 原因は切り抜き位置のずれ（進化後の枠や光る演出でバッジの位置が数ピクセル動く）。
  一方の中央部分をもう一方の中でずらしながら比べる方法に変えたところ 37 グループに減り、
  しきい値を 0.6〜0.75 で変えてもグループ数が変わらない（同じカードと違うカードの差がはっきりしている）
- 一覧画像を目視した範囲では、違うカードが同じグループに混ざった例はなかった

## 結果
- サンプル 3 試合のターン開始時・終了時のフレームから 137 枚を集め、37 グループにまとまった（約 10 秒）
- 照合を盤面の読み取りに組み込み、`wbcc show` で場のフォロワーをグループ番号（名前を付ければカード名）で表示できる

- 手札のカードの特定（対戦中の画面は大きく表示される。リプレイは重なっている）

# 2026-09-29（続き）M3：手札のカードの特定

## やったこと
- 手札のカードを、左上の緑のコスト表示を基準に切り出し、コストを読み、見本と照合するようにした
- 場のグループと手札のグループを自動で結び付け、どちらか一方に名前を付ければ両方に付くようにした
- `wbcc show --hand` で手札（カード名とコスト）も表示する

## わかったこと
- コスト表示は色だけでは見つけにくい（プレイできるカードは縁全体が緑に光る）。円の形で探す（Hough 変換）と確実に見つかった
- 手札の表示は「リプレイか対戦中か」では決まらない。対戦中の画面も普段は右下に小さく重なって並び、
  マウスを重ねたときなどに大きく広がる。両方の形で探して多く見つかった方を使う
- 手札の攻撃力・体力のバッジは誤読が多かった（「0」の読み落とし、「54」など）。誤った値は害になるので読まないことにした
- 場のイラストは手札のイラストを 0.6〜0.75 倍にしたものに相当し、この縮尺で比べると同じカードは 0.93 以上で一致した。
  37 × 38 グループを比べ、「0.75 以上、2 番目との差 0.15 以上」で結び付けた 8 組はすべて正しかった
- ターン開始時は、引いたカードが手札の列に入る前に手札の上に大きく表示される。そのため手札の枚数表示と
  列のカードの数が 1 枚ずれる。枚数表示が 1 枚多いときは、大きく表示されたカードを引いたカードとして加える
- コストは効果で変わる（例：リュミオール&アルジャンテが 8 → 3）。読んだ値は画面の表示どおり

## 結果
- 手札のカード：新たに 38 グループ（場と合わせて 75 グループ）。場と手札の 8 組を自動で結び付けた
- 手札の枚数表示と見つかったカードの数の一致：94 フレーム中 78（83%）。合わないフレームは警告を付ける
  （カードを出す演出の途中、手札の表示が切り替わる途中など）

- M4：効果を考えない攻撃の組み合わせの探索とリーサルの計算
